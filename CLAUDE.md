# Notes for Claude sessions in this repo

## Always merge to main
The site owner wants every push merged into `main` right away.
1. After pushing your working branch, run `git fetch origin main`.
2. If `main` has moved, merge `origin/main` into your branch and push the branch again.
3. Then fast-forward `main` with `git push origin HEAD:main`.

## Going live
`main` is what runs on webburrito.com (Firebase Hosting, project `web-burrito`), but only after a deploy:
- Pushing to `main` deploys the site (Firebase Hosting) automatically: `.github/workflows/firebase-hosting-merge.yml` signs in to Google with Workload Identity Federation (set up Nov 6, 2026; README, "Automatic deploys"). There's no key: the project's organization blocks service account keys. Check the run with `gh run list -R youngk4u/Webburrito -L 1`; if it ever says "Skipping deploy", that sign-in broke, so tell the owner.
- Changes to `functions/` or `firestore.rules` always need `firebase deploy --only functions,firestore`.

## Things to know
- The site is served from the repo root. Anything that isn't meant for the web must be in `hosting.ignore` in `firebase.json`. A predeploy check (`tools/check_deploy.mjs`) stops any deploy that would publish files that aren't in git.
- Previews (`<slug>/index.html`) are an encrypted payload inside `tools/preview_gate.html`. After changing the gate, run `python3 tools/rewrap_previews.py`. Never edit a payload.
- Each preview has a personal link, `https://webburrito.com/<slug>/#k=<secret>` (`tools/preview_crypto.py`): it opens the preview without the passcode, and only a claim made with it launches without the admin's owner check. The repo is public, so never commit, paste or log a personal link or its secret; they live in the sheet (Preview link column) and the pitch emails. `build_previews.py` prints new ones and keeps a preview's link when it's rebuilt; `preview_links.py` gives older previews one or replaces one (`--new`). Both need `PREVIEW_PASSCODE` from the environment.
- Industry pages, the pricing guide, the 404 page and the sitemap are generated by `python3 tools/build_pages.py`. A page's date (sitemap `lastmod`, the guide's "Updated", the legal pages' "Last updated") only changes when that page's content does; the sitemap's `home page` fingerprint does the same for the hand-edited `index.html`. Don't restamp dates by hand.
- README.md explains the previews, tracking, `/admin/` and setup.
- The customer platform (`app/`, `functions/app/`, functions `app` and `launcher`) needs four secrets in Secret Manager (README, "Customer platform"). It isn't deployed at all until `PLATFORM=on` in `functions/.env` (so deploys don't stop to ask for missing keys); `/app/` shows "Coming soon" meanwhile. Once on, it runs in test mode (Square sandbox, no domains bought) until `SQUARE_ENVIRONMENT=production`.
- Test platform changes against stand-in servers, never the real Claude, Square or Cloudflare APIs: `functions/.env.local` + `functions/.secret.local` (git-ignored) override the base URLs and keys for the emulators.
- Claiming a preview (`/app/?claim=<slug>`, from the "Make it mine" button the preview gate adds once sign-ups are open; with the personal link's key, or the passcode, which sets `claim.verified: false` so `ensureDomain` waits for the admin's "Approve owner and launch") runs `livePreview()` in `functions/app/site.js` (concept banner, noindex, forms, dead buttons out) plus one AI polish pass. It is still AI-checked before it goes live, but the check is told that the ratings and review quotes in it (saved as `claim.listingLines`) came from the business's public listings. If the preview kit changes its class names (`wb-concept`, `wb-credit`), update `livePreview()` and its tests. After changing `tools/preview_gate.html`, run `python3 tools/rewrap_previews.py`.
- Customer accounts: email and password, or Google. No emailed sign-in links: one would open an account a stranger had set a password on. Confirm and new-password links land on `/app/` (`mode`, `oobCode`), and a confirm link is only used while logged in to that account. `signedIn()` lets an unconfirmed email in, but the routes in `NEEDS_CONFIRMED_EMAIL` (`functions/app/index.js`: paying, domains, publishing, email, card, cancel) and admin rights need a confirmed one. Any new route that spends money or acts on a domain goes in that list.
- The `/app/` builder: the preview iframe is sandboxed (`allow-scripts`, never `allow-same-origin`) and `guarded()` adds the only script allowed in it (a nonce in a CSP meta), which keeps links from navigating it away. Build progress lives in `users/{uid}/site/progress`. Don't add writes at the very end of a build: a burst of writes to documents the page listens to made the Firestore emulator stop sending updates (Nov 2026). `/api/app/config` lists `features` the server supports, so a newer page (published on every push) doesn't offer something before the server for it is deployed.
- Owner go-live: `bash tools/go_live.sh` (keys typed by the owner, straight into Secret Manager). Never ask for or handle the key values yourself.
- Platform rules to keep: every launch step must be safe to run twice; a `domainIndex/{domain}` entry marked `registered` stays with that customer for good (never deleted or reassigned); Square customers are kept per environment (`squareCustomers.{sandbox|production}`, `customerIndex/{env}_{customerId}`); a refund or dispute only ends a plan when it's on that plan's own payment.
